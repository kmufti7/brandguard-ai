# ADR-002: RAG Copy Generation

**Status:** Accepted (paper)
**Date:** 2026-05-09
**Deciders:** Kamil Mufti
**Component:** RAG Copy Generation Agent

---

## Context

Marketing copy generated by an LLM without grounding tends to drift from brand voice and to fabricate product details. BrandGuard's value depends on copy that (a) sounds like the brand, (b) is factually anchored to product source documents, and (c) carries citations that a legal reviewer can verify. The MVP scope is one product line with three to five SKUs, which makes a constrained RAG setup viable without sharding or per-product index management.

The agent has three responsibilities:

1. Retrieve relevant chunks from the brand voice document and the product fact sheet for a given prompt.
2. Generate copy that uses those chunks and cites them inline.
3. Reject any generation in which a factual claim is not citation-backed.

---

## Decision

Build a RAG Copy Generation Agent that retrieves over the brand voice document and the product fact sheet, generates copy with inline citations, and enforces a deterministic citation check before returning output. Scope is restricted to a single product line with three to five SKUs.

### RAG sources

Two source documents in MVP:

1. **Brand voice document.** Tone guide, prohibited language, preferred phrasings, audience-style mappings. Authored once, version-controlled. Indexed at the paragraph level.
2. **Product fact sheet.** Per-SKU specifications: features, pricing tiers, inclusions, geographic availability, regulatory notes (telecom-flavored). Indexed at the field level (one chunk per fact) so a citation maps to a single verifiable fact.

A third source category (campaign-specific brief) may be added in Session 2; for MVP the brief is passed inline as part of the prompt rather than indexed.

### Citation-required output

Generated copy must include inline citations of the form `[brand_voice:§3.2]` or `[fact_sheet:SKU_PRO5G:price]` against every factual claim. The model is instructed at generation time to cite or to omit the claim. After generation, a deterministic citation check parses the output, extracts every cited reference, and validates each one:

- Does the cited chunk ID exist in the index?
- Was that chunk actually retrieved for this request (i.e., is it in the working context window)?
- Does the cited claim match the chunk content (string-overlap heuristic with a configurable threshold)?

Any failure of the citation check causes the generation to be rejected. The agent returns a structured rejection (which check failed, on which claim, citing which chunk) rather than the unverified copy. Rejections are logged via the WORM Logger and surface to the caller as a 4xx-style error indicating regeneration is required.

The citation check is deterministic Python code, not an LLM judge. This is required by DNA §8 (decisions that gate release must be deterministic verification, not LLM-judged routing).

### Brand voice integration approach

The brand voice document plays two roles in generation: it is a retrieval source AND a system-prompt style guide. The two roles are complementary, not redundant.

1. **As a retrieval source.** The voice doc is indexed at the paragraph level and retrieved alongside product-fact chunks. Every claim or framing rule that maps to a voice section gets cited inline (`[brand_voice:§3.2]`). This is the auditable surface: a reviewer following a citation lands on the exact rule that was applied, and a voice-doc update is a document change rather than a prompt-engineering pass.
2. **As a system-prompt style guide.** A short, stable summary of the voice doc (tone descriptors, prohibited language list, preferred phrasings) is rendered into the generation system prompt. This biases the default style of generations even when retrieval does not surface a specific voice paragraph for a given prompt. The system-prompt summary is generated from the voice doc deterministically (template fill from voice-doc front matter), so the two views never drift out of sync.

Why both: retrieval-only handling leaves a default-style gap when the prompt does not surface a relevant voice paragraph; system-prompt-only handling has no citation trail and cannot be reviewed at the per-claim level. Combining the two keeps citations auditable for specific rules while ensuring a brand-aligned default tone for everything else.

The brand voice document carries section IDs (`§1.1`, `§3.2`, etc.). Citations preserve those section IDs, and the system-prompt summary preserves the same IDs in inline references so the reviewer can trace either path back to the source rule.

### Single product line, 3-5 SKUs scope

MVP indexes one product line. Multi-product-line support requires either a per-product retrieval router or a shared index with explicit product-tier filtering at query time. Either is implementable; both add surface area that is not justified before the single-product MVP is validated. Re-evaluate in Session 5 or later.

### Generation request flow

1. Caller provides: audience definition (from Audience Discovery Agent), campaign brief, generation parameters (length, format, tone hint).
2. Agent retrieves top-K chunks from brand voice and product fact sheet using the campaign brief and the audience summary as the query.
3. Agent calls foundation model with retrieved chunks, citation instruction, and structured output schema.
4. Citation check runs on the returned text. Pass: return copy + citations + retrieval metadata. Fail: return rejection with reason.
5. Token FinOps Tracker records input tokens, output tokens, model identifier, retrieval call cost, citation-check pass/fail status. WORM Logger appends the full request/response/decision record.

## Consequences

### Positive

- Deterministic citation check is independently testable and aligns with DNA §8
- Brand voice is reviewable and updatable without re-engineering prompts
- Per-SKU fact-sheet chunking gives precise citation granularity
- Rejected generations are first-class outputs (logged, surfaced) rather than silently absorbed
- The MVP scope is small enough to ship without RAG architecture overhead (no router, no per-tenant indexes)

### Negative / accepted trade-offs

- Strict citation enforcement will reject some generations that are factually correct but did not cite. Acceptable: the rejection prompts regeneration with a stricter cite instruction; the alternative (release uncited copy) violates the gate.
- Single-product-line scope means BrandGuard cannot demonstrate cross-product copy in MVP. Out of MVP scope on purpose.
- The string-overlap citation match has false positives (irrelevant chunks that happen to share words) and false negatives (citations to paraphrased content). Configurable threshold is the mitigation; tightening or loosening it is a Session 4 evaluation decision based on golden dataset behavior.

---

## Alternatives Considered

- **System-prompt-only brand voice (no RAG over the voice doc).** Rejected: not auditable, no citation trail at the per-claim level, and brand voice updates require prompt re-engineering. The accepted approach uses the system prompt as a stylistic floor while retaining the voice doc as a retrieval source for auditable citations.
- **RAG-only brand voice (no system-prompt summary).** Rejected: leaves a default-style gap when retrieval does not surface a voice paragraph for a given prompt. The accepted approach combines retrieval-grounded citations with a deterministic system-prompt summary so default tone is brand-aligned even on prompts that do not pull voice context.
- **LLM-as-judge for citation verification.** Rejected: violates DNA §8 (deterministic verification required for release-gating decisions).
- **Multi-product retrieval router from day one.** Rejected: premature; single product line is sufficient to validate the rest of the architecture and ships faster.
- **Vector store other than FAISS.** Local FAISS is reused from ADR-001 for the same data-plane reasons.
