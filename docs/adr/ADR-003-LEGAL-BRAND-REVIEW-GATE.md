# ADR-003: Legal/Brand Review Gate

**Status:** Accepted (paper)
**Date:** 2026-05-09
**Deciders:** Kamil Mufti
**Component:** Legal/Brand Review Gate

---

## Context

Marketing copy generated by an LLM, even when grounded by RAG and citation-checked, must clear a human review step before release. Three reasons:

1. **Legal exposure.** Claims about pricing, availability, regulatory compliance, or comparative performance carry legal risk that automated checks do not catch.
2. **Brand judgment.** Brand leads need to approve tone, framing, and positioning that are subjective and not encodable as rules.
3. **Audit-trail necessity.** A reviewer's explicit approve/reject is the artifact that anchors downstream accountability.

Skipping the gate or making it advisory creates exactly the failure mode BrandGuard exists to prevent. The gate must therefore be fail-closed: nothing is released without explicit approval (or an explicit whitelist match for low-risk categories defined ahead of time).

The gate also sits at a release boundary, so its routing logic (route to reviewer, auto-pass on whitelist, auto-block on blacklist) cannot be LLM-judged. Per DNA §8, decisions that gate release must be deterministic verification, not LLM-judged routing.

---

## Decision

Build a Legal/Brand Review Gate as a human-in-the-loop, fail-closed component that extends the Kill-Switch Guard primitive from `intelliflow-core` v2. Routing is deterministic rule evaluation. Approval and rejection both write to the WORM Logger. No release path bypasses the gate.

### Fail-closed semantics (extends Kill-Switch Guard)

The Kill-Switch Guard primitive in `intelliflow-core` v2 is the canonical fail-closed enforcement primitive across IntelliFlow products. The Legal/Brand Review Gate inherits two of its properties:

1. **Default deny.** If any precondition for release is missing (no reviewer decision, missing citations, expired whitelist entry, kill-switch tripped at the system level), the output is blocked, not released.
2. **Tripped state is sticky.** If the global kill-switch is tripped, the gate refuses to evaluate new requests until the kill-switch is explicitly reset by an operator. This prevents a single bad reviewer decision or a system-wide policy change from leaking copy that should be held back.

Extension means the gate adds review-specific state (pending reviews, reviewer assignments, whitelist/blacklist tables) on top of the kill-switch primitive without modifying the primitive itself. The primitive stays generic; the gate is the marketing-specific specialization.

### Decision rule: deterministic verification, NOT LLM-judged routing

When a generation arrives at the gate, three deterministic checks decide routing:

1. **Whitelist match.** Does the audience segment + copy template combination match an entry in the pre-approved whitelist (e.g., "transactional account-update notices to existing customers")? If yes and unexpired, auto-pass. Whitelist entries are added by a human ahead of time and have explicit expiration dates.
2. **Blacklist match.** Does the copy contain any phrase from the blacklist (regulated medical claims, comparative performance claims, financial guarantees, etc.)? If yes, auto-block with the matched phrase recorded.
3. **Default route.** If neither matched, route to a human reviewer.

All three checks are deterministic Python: regex, set membership, structured-table lookup. There is no LLM judge in the routing path. This is required by DNA §8, which forbids LLM-judged decisions at release-gating boundaries because their failure mode is silent and non-reproducible.

LLM judgment is allowed in two adjacent surfaces:

- **Pre-routing summary for the reviewer.** An LLM may produce a one-paragraph English summary of the copy + retrieval grounding to help the human reviewer; this summary does not gate the decision.
- **Post-decision rationale capture.** When the human reviewer rejects, an LLM may suggest possible reasons; the reviewer chooses or overrides. This is feedback, not routing.

Neither of these LLM uses is on the routing path.

### Approval workflow

```
generation arrives at gate
  -> deterministic blacklist check
       FAIL: auto-block, log via WORM, return rejection to caller
  -> deterministic whitelist check
       MATCH (unexpired): auto-pass, log via WORM, return approval
  -> default: route to reviewer queue
       reviewer assigned, notification sent (out-of-band channel)
       reviewer sees: copy, citations, retrieval grounding, audience definition, generation parameters
       reviewer chooses: APPROVE / REJECT / REQUEST_CHANGES
       decision logged via WORM with reviewer ID and timestamp
       caller polls or receives webhook on decision
```

Reviewer assignment is round-robin within an assigned reviewer pool defined per copy category. No LLM-based reviewer assignment.

### Reject path

A rejected generation:

- Is logged to WORM with reviewer ID, reason category (chosen from a fixed list), and free-text reason
- Is returned to the caller with a structured rejection object
- Is NOT silently regenerated; the caller must explicitly re-submit a new generation request
- Is added to a rejection corpus that informs future eval golden-dataset additions (Session 4) but does NOT feed back into generation training in MVP

### Audit logging via WORM Logger

Every gate decision (auto-pass, auto-block, route-to-reviewer, reviewer approve, reviewer reject) writes a record to the WORM Logger with:

- Decision type
- Decision actor (system/whitelist, system/blacklist, reviewer ID)
- Decision timestamp
- Generation ID, audience ID, retrieval call IDs
- Inputs to the decision (matched whitelist row, matched blacklist phrase, reviewer free-text)
- Resulting state (released, blocked, pending)

WORM records are append-only and serve as the legal audit artifact for any post-hoc dispute about whether and why a piece of copy was released.

---

## Consequences

### Positive

- Release gate cannot be bypassed; default-deny is enforced at the primitive level
- Routing decisions are reproducible and reviewable in code
- LLM use is scoped to non-gating surfaces (summary, rationale capture), preserving DNA §8
- Whitelist/blacklist mechanism gives marketing teams a way to scale approvals on transactional or low-risk categories without weakening the gate for novel copy
- Kill-switch primitive is a single shared surface across IntelliFlow products; tripping it has consistent semantics

### Negative / accepted trade-offs

- The gate is a hard latency cost on novel copy (reviewer-bound, hours to days). Acceptable: the alternative is unreviewed release, which is the failure mode BrandGuard prevents.
- Whitelist maintenance is a human cost. Required: whitelist entries expire and must be re-affirmed; this is a feature, not a bug.
- Reviewer assignment is round-robin, not load-balanced or skill-routed. Future enhancement; not in MVP scope.
- Rejected generations do not auto-improve the system. By design for MVP: feedback loops on a release gate are a separate decision and require their own ADR.

---

## Alternatives Considered

- **LLM-judged routing (LLM decides whitelist/blacklist/route).** Rejected: violates DNA §8. The failure mode of an LLM router at a release boundary is silent and non-reproducible.
- **Advisory gate (warn but release).** Rejected: an advisory gate is not a gate. It would be misleading to call this component a review gate without enforcement.
- **Per-output approval threshold based on hallucination eval score.** Rejected: a release gate should not depend on a probabilistic input. The eval score informs offline regression, not per-output release.
- **Reviewer-replacement by a fine-tuned classifier.** Rejected for MVP. Classifiers can be added as auto-pass extensions of the whitelist surface in a later session, but the human reviewer remains the default routing target.
